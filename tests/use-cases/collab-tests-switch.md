# Use case: the owner switches where the tests run, and sees it in the status line

Zach runs a collab on PR #1 with Codex. The repo's `.collab.json` doesn't say where the tests run, so they run on the agents' machines, which takes two hours. The team's CI runners take 15 minutes. On `main`, `ci.yml` runs on pull requests and has a `workflow_dispatch` trigger, `lint.yml` has no such trigger, and `deploy.yml` runs only by hand, with the production secrets. A colleague runs their own collab on PR #6 of the same repo.

1. **Seeing where the tests run.** Zach types `/collab tests` in Claude Code. The skill runs `collab tests` and shows its output. PR #1 runs the tests on the agents' machines, with `node --test` in each task's worktree. New collabs in this clone do the same, by default. The output says how to switch, and that PR #6 belongs to another GitHub account, so collab leaves it alone (`collab tests --pr 6` says so too).
2. **The status line says it too.** Zach's Claude Code status line already shows his usage. He wraps that command in collab's: `node "$HOME/.collab/bin/collab.mjs" statusline -- <his command>`. His usage line now ends with `(tests local)`. It reads only this clone's git data, never GitHub, so it stays fast. Outside a git repo it adds nothing. On Windows a wrapped command other than `node` runs through `cmd.exe`, so status lines installed with npm (`.cmd` files) work too.
3. **Moving the tests to CI.** Zach types `/collab tests remote`. collab doesn't know which workflow runs the tests, so it asks, and lists the workflows on `main` that it can start: `ci.yml` and `deploy.yml`, not `lint.yml`. Asking for `lint.yml`, which can't be started, or for a file that isn't there, is refused, and nothing changes. From Claude Code, `deploy.yml` is refused too: it doesn't run on pull requests and `.collab.json` doesn't name it, and an agent talked into it would run the agents' code with the production secrets. Only Zach's own terminal can name such a workflow. He types `/collab tests remote --workflows ci.yml`. collab records that in PR #1's ledger, then in this clone's git config; PR #6 stays as it was.
4. **The agents follow.** Codex's next command shows an inbox line saying the owner moved the tests to CI (`ci.yml`). Its next `collab verify` starts `ci.yml` on the task's branch instead of running the tests. The status line now ends with `(tests remote)`, in the clone and in a task's worktree. Codex submits T1 while CI runs, and Claude approves it before CI is done.
5. **Only the owner switches.** A session started for one agent (with `COLLAB_AGENT` set by `collab invite`) can run `collab tests` to read the setting. `collab tests local` there is refused as the owner's switch.
6. **Back to the machines.** CI turns out to be slow today, so Zach types `/collab tests local`. What already passed still counts, and the status line ends with `(tests local)` again. T1 was approved while its CI ran, and that CI never finished, so nothing has passed at its head: Codex's `collab next` says to run the tests, and `collab merge T1` refuses until they pass. Codex's `collab verify T1` runs them on the machine, without starting CI. The run collab started earlier still shows among the sub-PR's checks, so the merge waits for GitHub to finish it, and says why. Then T1 merges.
7. **New collabs.** Zach's choice is kept in this clone's git config (`collab.tests`, `collab.ciWorkflows`). A collab started later in this clone starts with it, though `.collab.json` doesn't say so.
