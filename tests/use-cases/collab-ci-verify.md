# Use case: the tests run on CI, alongside the review

Zach's test suite takes two hours on an agent's machine and 15 minutes on the team's CI runners. His workflows only run for PRs into `main`, so sub-PRs get no checks. He adds this to `.collab.json` on the default branch:

```json
{ "verify": "ci", "ciWorkflows": ["ci.yml"] }
```

`ci.yml` has a `workflow_dispatch` trigger, so collab can start it on any branch, even while a sub-PR is a draft.

1. **Joining.** `collab join` says that `collab verify` runs the tests on CI, names the workflows, and leaves out the warning that sub-PRs get no checks. A listed workflow that the default branch lacks, or that has no `workflow_dispatch` trigger, gets a warning at join. `"verify": "ci"` without `ciWorkflows` is ignored with a warning, and verify runs locally as before. collab reads all of this from the default branch, so a task's branch can't switch it.
2. **Verify starts CI.** Codex claims T1, pushes, and runs `collab verify T1`. No tests run on its machine. collab starts `ci.yml` on T1's branch and records that CI runs at that commit. It tells Codex it doesn't have to wait. Running `verify` again while CI runs reports how far it is and never starts a second run.
3. **Submit alongside CI.** `collab next` tells Codex to submit, and `collab submit T1` puts T1 in review at once, with CI still running. The reviewer, Claude, reads the diff and runs no tests (`review-claim` says so). It may approve while CI runs, and its review comment says CI is still running.
4. **The merge waits for CI.** `collab merge T1` refuses while CI runs. `collab status` has a CI column. A run that a push or a PR event started at the same commit doesn't count: only the runs collab started do. When the run passes, Codex's `collab next` records the result and says to merge. Before merging, collab asks GitHub again. If someone reran the workflow on GitHub and it failed, the merge is refused and that failure is recorded, so `next` sends T1 back to Codex instead of offering the merge again. Codex reruns CI, it passes, and T1 merges.
5. **CI fails.** CI fails on T2 after the submit. Codex's `next` says `fix T2`, with the failing workflow and its link. Claude's `next` says to request changes, and an approval is refused. The dashboard shows CI as failed. If the failure looks flaky, `collab verify T2` at the same commit runs CI again. After Codex pushes a fix, T2 is still in review, and Codex's `next` says to start CI on the new commit. Claude checks out the new commit and approves once CI passes.
   - **CI fails after the approval.** Claude approved T5 while its CI ran, and then CI fails. Codex's `next` says `fix T5`. Codex's fix sends T5 back to review, because the approval was for the old commit. Codex runs `collab verify` and `collab submit` as usual. Submit says T5 is already in review and there is nothing to submit, so it doesn't fail. Claude reviews the new commit, CI passes, and T5 merges.
6. **A task that changes a workflow.** The owner allowed T3 to change `ci.yml`. CI on T3's branch would run T3's own changed workflow, so `collab verify T3` runs the tests on the machine instead and says why. That verify counts for the submit and the merge. `review-claim` tells Claude, the reviewer, the same: run `collab verify T3` on the machine before approving. For any other task, a verify from a machine doesn't count while the tests run on CI.
7. **CI that can't start.** If GitHub can't start a workflow (it has no `workflow_dispatch` trigger), verify fails with the reason and records nothing. A started workflow with no run after 15 minutes counts as failed ("did not start"), and so does a run still waiting for a runner after an hour (the runners are down or all busy). Either way the owner is told to run verify again, and to check the runners.
