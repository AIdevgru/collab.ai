# Use case: CI runs fast where agents wait on it, and in full before main

1. Zach runs `/collab <PR> --sessions 4` on a PR into `main`. Four Claude sessions and a Codex each push draft sub-PRs into the PR branch.
2. Each sub-PR's CI runs on Linux only, on node 22 and 24, with the suite split into 3 shards. Each shard takes about 2 minutes, not the 6 a single Linux job took. Sub-PRs no longer start Windows jobs, which took about 19 minutes and count double against a private repo's minutes.
3. With CI verify on (`"verify": "ci"`), `collab verify` dispatches the workflow on the task branch. That run is the same Linux tier.
4. Each merged task moves the main PR's head. The main PR targets `main`, so its CI runs the full matrix: Linux and Windows, node 22 and 24, 3 shards each. Each Windows shard takes about 7 minutes. Zach merges the main PR only after that is green, so a Windows-only break is caught there, as a red main PR CI and a fix-ci task.
5. Pushes to `main` run the full matrix too. To run Windows on another branch, Zach dispatches CI with "full" checked.
6. A stacked PR into another feature branch gets the Linux tier, like a sub-PR, until it is retargeted to `main`.
7. The shards are split by time, not by name. A private repo's runner has 2 cores, so node runs the test files one at a time, and a shard takes as long as its files together. node's own `--test-shard` dealt the sorted files out in turn and put three of the slowest in shard 2: 11 minutes on Windows while shard 1 took 4. `scripts/test-shard.mjs` places the files slowest first, each in the shard with the least time so far, using the times last measured on that OS (`scripts/test-times.json`). Every shard comes out within a few seconds of the others.
8. Zach adds a test file. It has no time yet, so it counts as the median file and lands in the lightest shard. Each CI job logs a `Test times on <os> (ms)` line, and after a full run Zach refreshes the times with `gh run view <run id> --log | node scripts/test-shard.mjs --update`. A file the logs miss, as from a cancelled shard, keeps its old time, and a deleted file drops out.
9. When someone adds a shard, the job name, the shard list and the script's argument must agree. Every file `npm test` runs must be in exactly one shard, and the lowest node in the matrix must be the one `engines` names. The tests check all of these.
