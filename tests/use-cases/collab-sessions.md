# Use case: running several Claude sessions in parallel on one PR

Zach has a collab on PR #1 with five tasks: T1, T2 and T3 can start at once, while T4 and T5 wait on T1. He wants it built faster than one Claude session can, so he asks for parallel sessions instead of opening more terminals himself.

1. In Claude Code he types `/collab https://github.com/o/r/pull/1 --sessions 4`. Claude joins, writes the plan, and then, because he asked for four sessions and it is one of them, runs `collab invite claude --sessions 3 --pr 1 --agent <its id>`. From his own terminal he could run the same command without `--agent`.
2. `invite --sessions` starts a **session keeper** for the PR. It starts only as many sessions as there are tasks they can take now, and gives each one its own task, reserved for it so no other agent takes it first. With `--agent`, one task is always left for the agent that asked while it is free.
   - With three tasks ready and Claude free, it starts two headless sessions, for T2 and T3, and Claude itself claims T1.
   - Two tasks whose scopes overlap never get sessions at the same time, since only one of them could be claimed. If Claude's own session ends and it isn't seen for 30 minutes, the task it was holding back goes to a session.
   - The sessions sign in the way Zach's own Claude does (his `CLAUDE_CODE_*` setup carries over, including to sessions started later), but they don't inherit his session's markers.
   - The output says which sessions started on which tasks and that more start as tasks unlock. It also says the keeper stops at its timeout (two hours unless he passes `--timeout`), and that `collab stop --pr 1` stops everything. Since only Claude has joined, it also says the sessions review each other's tasks, and that an agent from another vendor would review first, with how to invite Codex.
   - Each session's startup prompt says it is one of up to three parallel sessions, each on its own task, and to tell the others with `collab msg` when it changes something they rely on.
3. `collab status --pr 1` shows a **Sessions** line: how many of the three are running, which session has which task, and when the keeper stops.
4. **More work, more sessions:** when T1 is done, T4 and T5 unlock. Within a round (about 20 seconds) the keeper starts one more session, which makes three. When Claude finishes T1 and is free, the keeper leaves it one of the two tasks. A cancelled dependency unlocks its dependents the same way.
5. **A session that stops mid-task:** a session's process ends while its task is still claimed, so its lease expires at once. The keeper then starts a new session that takes the task over with `claim --steal`. The branch and commits so far are kept.
6. **Asking for too many:** asking for more sessions than a plan can have tasks (12 by default) runs at most that many. A second `invite --sessions` while a keeper runs on the PR is refused: he ends the first with `collab stop --run <keeper id> --pr 1` (its sessions keep working), then invites again. `--sessions 0`, `--sessions two`, and `--sessions` together with `--task` or `--review` are refused, and so is `--agent` with an id that hasn't joined.
7. **When sessions can't start:** if two sessions in a row stop without doing any work (say Claude isn't signed in), the keeper stops starting them. `collab status` says why and where the session's error log is. If the agent's program can't be started at all, `invite` says so straight away.
8. **Reviews:** the sessions review each other's tasks; nobody reviews their own. An agent from another vendor goes first when one is around (see the review story), so Zach can still add Codex. When a task waits for a review that no free agent may take (its owner can't, and the others are busy), the keeper starts a session to review it. The keeper's output names it as `(reviews T1)`, and so does `collab status`. A review held for another vendor starts no Claude session until it opens to Claude.
9. **No collab yet:** on a PR without a collab, the keeper starts one session, which starts the collab and writes the plan. The rest start once the plan is posted.
10. **The end:** once every task is done or cancelled, or the collab is closed, the keeper exits by itself, and so does every session. `collab close` stops the keeper too, so after `close --purge` nothing starts a new collab on the PR. `collab stop --pr 1` stops the keeper first, so nothing new starts, then every session. A session that was starting at that moment is stopped as well. Their reserved tasks are released and their leases expire, so other agents can take the work at once. An agent session can't run the keeper itself, or a second `invite`.
