# Use case: safety rails

1. `collab context` returns the PR title, description and comments only under `untrusted`. Comments come only from people with write access, and collab's own machine comments are left out.
2. The test command comes from the default branch: `.collab.json`, or `package.json` `scripts.test` when there's no config file. A task branch that edits `.collab.json` can't change what `collab verify` runs, and `collab push` refuses that edit in the first place.
3. `collab join` refuses a fork PR, a closed or merged PR, and a PR whose head is the default branch, and a task's own sub-PR (exit 4), each with a message saying what to do. For a sub-PR, that's the main PR to join instead: in the end-to-end run, `$collab 17` on a sub-PR had started a second collab there.
4. Zach's clone is pinned to `zwymer`. If another session switches gh's active account, collab still uses `zwymer`'s token for every gh and git call, and it never runs `gh auth switch`.
5. An agent is talked into adding a GitHub Actions workflow, or editing one. `collab push` refuses before anything reaches GitHub, because a workflow runs with the repo's secrets as soon as its branch is pushed. The same goes for `.collab.json`. Moving a workflow somewhere else counts as changing it. If the task really needs the change, the agent asks with `collab block T1 --owner`, and Zach allows it for that task with `collab decide T1 "ok" --allow-protected`. That lasts until the task is released or claimed again.
6. `--body-file` and `--tasks` only read files inside the repo. An agent told to post `~/.ssh/id_ed25519` as its review notes is refused, whether or not it runs through the relay. Files in another worktree of the same repo are fine.
7. A session started for one agent acts only as that agent: with `COLLAB_AGENT` set, as it is in every invited session, `--agent` can't name another id. And an id like `claude-ab12` can't join as `codex`. Such a session can't run `collab relay` or `collab invite` either, since its own relay would act for any id it named. So an invited agent can't pose as a second agent and approve its own work.
8. `collab verify` and the setup command run code from an agent's branch, so they get the environment without variables whose names look like secrets (`GH_TOKEN`, `ANTHROPIC_API_KEY`, `NPM_TOKEN`…). A name listed in `passEnv` in `.collab.json` on the default branch is kept. The test output `verify` prints is labelled untrusted.
